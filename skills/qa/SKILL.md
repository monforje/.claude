# QA: проверка изменений

Навык для систематической проверки кода перед мержем. Цель — найти дефект, а не подтвердить, что всё хорошо.

## 1. Определи объём

```bash
git diff --stat $(git merge-base HEAD origin/main)..HEAD
```

Проверяешь: изменённые строки, их вызывающих и то, что от них зависит. Всё остальное — вне объёма, если явно не попросили обратное.

## 2. Запусти существующие проверки

Найди команды проекта, не выдумывай свои:

```bash
cat package.json 2>/dev/null | grep -A20 '"scripts"'
cat Makefile 2>/dev/null | grep -E '^[a-z-]+:'
ls .github/workflows/ 2>/dev/null
```

Порядок: типчекер → линтер → юнит-тесты изменённых модулей → полный прогон. Быстрые проверки первыми: они отсекают половину проблем за секунды.

Вывод команд приводи фактически. Если что-то не запустилось — это отдельная находка, а не повод пропустить шаг.

## 3. Разбери диф враждебно

По каждой изменённой функции пройди чек-лист из `references/checklist.md`. Ключевые категории:

- **Границы:** пусто, ноль, один элемент, максимум, отрицательное, переполнение.
- **Ошибки:** что происходит при исключении, таймауте, отказе внешнего вызова.
- **Состояние:** повторный вызов, параллельный вызов, вызов в неверном порядке.
- **Контракт:** изменилась ли сигнатура/формат ответа так, что ломает вызывающих.

## 4. Закрывай дыры тестами

Тест пишется в стиле существующих тестов проекта: тот же фреймворк, те же хелперы, то же расположение файлов. Сначала посмотри соседний тестовый файл, потом пиши.

Для найденного бага порядок строгий: тест, воспроизводящий баг → убедиться, что он падает → фикс → убедиться, что проходит.

## Запрещено

- Отключать, скипать, помечать как ожидаемо падающий или удалять тест ради зелёного прогона.
- Объявлять падение флаком без доказательства (падает и на базовой ветке / упал до выполнения тела теста).
- Расширять объём правками, о которых не просили.
- Сообщать об успехе, не прогнав проверки.

## Отчёт

```
## Что проверено
<команда> — <результат>

## Находки
1. [блокер|важно|мелочь] <файл:строка> — <дефект>
   Воспроизведение: <вход> → <фактический результат>, ожидалось <...>

## Покрытие
<что осталось непроверенным и почему>

## Вердикт
<готово к мержу | блокеры: ...>
```

Если находок нет — напиши это одной строкой, не добирай объём стилистическими замечаниями.
