# k6 recipes

Everything here assumes `k6 run script.js`. k6 is a single Go binary; the script
is JavaScript but there is no Node runtime — no `require`, no npm packages that
touch the filesystem or the network, `import` from `k6/*` modules only (a bundler
is needed for anything else).

## Script skeleton

```javascript
import http from 'k6/http';
import { check, sleep, group } from 'k6';

export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: 400, timeUnit: '1s',        // 400 requests/s offered, whatever the system does
      duration: '15m',
      preAllocatedVUs: 200, maxVUs: 800,
      tags: { phase: 'steady' },
    },
  },
  thresholds: {
    'http_req_failed{phase:steady}': ['rate<0.001'],
    'http_req_duration{phase:steady}': ['p(95)<300', 'p(99)<1000'],
    'dropped_iterations': ['count<1'],   // generator kept up with the arrival rate
  },
  discardResponseBodies: true,           // override per-request where you assert on the body
};

const BASE = __ENV.BASE_URL;             // never hardcode a host; -e BASE_URL=...

export default function () {
  group('browse', () => {
    const res = http.get(`${BASE}/api/products?page=1`, {
      tags: { name: 'GET /api/products' },   // group by route, not by URL
      responseType: 'text',
    });
    check(res, {
      'status 200': (r) => r.status === 200,
      'has items': (r) => r.json('items').length > 0,
    });
  });
  sleep(Math.random() * 2 + 1);          // think time: 1–3 s
}
```

## Executors: pick the load model

| Executor | Model | Use for |
| --- | --- | --- |
| `constant-arrival-rate` | Open — N requests/s regardless of response time | Capacity and SLO questions. **The default choice.** |
| `ramping-arrival-rate` | Open, stepped rate | Finding the knee, stress, breakpoint, spike |
| `constant-vus` | Closed — N users, each waiting for its own response | Reproducing a fixed-concurrency client (a worker pool, a partner with N connections) |
| `ramping-vus` | Closed, stepped concurrency | "How many concurrent sessions before it breaks" |
| `per-vu-iterations` / `shared-iterations` | Fixed amount of work | Batch/throughput jobs, not user traffic |

The arrival-rate executors are what keep offered load honest when the system
slows down; see the coordinated-omission section in
`metrics-and-monitoring.md` for why that matters.

Arrival-rate executors need VUs pre-allocated. `preAllocatedVUs` too low and k6
starts dropping iterations (see `dropped_iterations` below); the estimate is
`rate × expected_latency_seconds`, with `maxVUs` well above it because latency
grows under load — which is the whole point of the run.

## Warm-up as its own scenario

Tagging the phases separates the cold window from the measured one, so the
thresholds only judge the steady state:

```javascript
scenarios: {
  warmup: { executor: 'constant-arrival-rate', rate: 50, timeUnit: '1s',
            duration: '2m', preAllocatedVUs: 50, tags: { phase: 'warmup' },
            gracefulStop: '0s' },
  steady: { executor: 'constant-arrival-rate', rate: 400, timeUnit: '1s',
            duration: '15m', startTime: '2m',
            preAllocatedVUs: 200, maxVUs: 800, tags: { phase: 'steady' } },
}
```

Then every threshold is written against `{phase:steady}`, as in the skeleton
above. Without the tag the warm-up latency is inside the p95 you report.

## Thresholds: pass/fail in the script

Thresholds are what make a k6 run a test rather than a measurement: a breached
threshold exits non-zero, so CI can gate on it. Express the criteria you fixed
before the run, per scenario or per route:

```javascript
thresholds: {
  'http_req_duration{name:POST /api/checkout}': ['p(95)<800'],
  'http_req_failed': ['rate<0.001'],
  'checks': ['rate>0.999'],
  'http_req_duration{phase:steady}': [
    { threshold: 'p(99)<2000', abortOnFail: true, delayAbortEval: '1m' },
  ],
}
```

`abortOnFail` stops the run once the system is clearly past the knee — useful on
a shared environment, and it keeps a breakpoint test from pounding something that
already failed. `delayAbortEval` prevents the first cold seconds from aborting it.

## Checks: assert every response

`check()` records a pass/fail rate; **a failing check does not fail the run on its
own**. That is the single most common way a k6 result lies: the system 500s under
load, `http_req_duration` looks excellent because errors are fast, and the run
exits zero. Two fixes, use both:

- A threshold on `checks` (`['rate>0.999']`) and on `http_req_failed`.
- Assert on the body, not only the status. An empty list, a JSON error envelope,
  and a cached stale page are all `200`.

`http_req_failed` counts transport failures and non-2xx/3xx by default; it does
not know that a `200 {"error": ...}` is a failure. Use
`http.get(url, { responseCallback: http.expectedStatuses(200) })` to narrow what
counts as success, or assert in a check.

## Test data

Per-VU data must not be per-VU *copies* — a 50 MB CSV loaded 800 times is 40 GB.
`SharedArray` keeps one copy across VUs:

```javascript
import { SharedArray } from 'k6/data';
import exec from 'k6/execution';

const users = new SharedArray('users', () => JSON.parse(open('./users.json')));

export default function () {
  const u = users[exec.scenario.iterationInTest % users.length];  // no repeats
  // ...
}
```

`open()` only works in the init stage (outside the default function). Picking by
iteration rather than randomly avoids the accident where every VU hammers the
same row and the database serves the whole run from one cached page — see the
data section of `scenarios.md`.

For login-per-iteration flows, authenticate in `setup()` once and pass tokens
through, or the run measures your identity provider.

## Metrics k6 gives you

| Metric | Meaning | Watch for |
| --- | --- | --- |
| `http_req_duration` | Full request, sending → body received | The headline latency; always read as percentiles |
| `http_req_waiting` | Time to first byte (server think time) | Splits server work from transfer; large gap vs `duration` means big bodies or a slow link |
| `http_req_connecting` / `tls_handshaking` | Connection setup | Non-zero at steady state means connections are not being reused |
| `http_req_blocked` | Waiting for a free connection or DNS | Rising = client-side saturation, not the server |
| `http_reqs` | Completed requests, with rate | The real throughput |
| `http_req_failed` | Failure rate | Pair with `checks` |
| `iterations` / `iteration_duration` | Whole scenario per VU | Where think time lives |
| `vus` | Active VUs | With an arrival-rate executor, a climb means the system is slowing |
| `dropped_iterations` | Iterations k6 could not start | **Offered load was below plan.** Raise `preAllocatedVUs`/`maxVUs`, or the generator is out of capacity. Any non-zero value invalidates the arrival rate you think you tested. |

## Output

The end-of-test summary is fine for a single run, but it is aggregated and gone.
For anything you will compare or chart:

```bash
k6 run -e BASE_URL=https://staging.example.test \
       --out experimental-prometheus-rw \      # live, joins the infra dashboards
       --summary-export=summary.json \         # machine-readable verdict (older k6)
       script.js
```

Output plugin names move between k6 versions — `k6 run --help` lists what this
binary has — and `--summary-export` is deprecated in favour of `handleSummary`,
so prefer the latter for anything permanent.

`--out json=raw.json` writes every sample — accurate percentiles later, but the
file grows fast, so use it deliberately. `handleSummary(data)` in the script lets
you emit exactly the report shape you need:

```javascript
export function handleSummary(data) {
  return { 'summary.json': JSON.stringify(data, null, 2) };
}
```

Sending metrics to the same Prometheus/Grafana the infrastructure uses is worth
the setup: generator-side latency and server-side saturation on one time axis is
how a bottleneck gets identified in minutes instead of an afternoon.

## Pitfalls

- **Failing checks that pass the run.** Covered above — threshold on `checks`.
- **`dropped_iterations` ignored.** You tested a lower rate than you reported.
- **URL-per-metric explosion.** `/users/42` and `/users/43` become separate
  metrics without `tags: { name: 'GET /users/:id' }`, and the percentiles become
  meaningless.
- **No think time.** Back-to-back requests from every VU is a stress pattern, not
  user traffic — it inflates concurrency and understates cache effectiveness.
- **`discardResponseBodies` left on** while a check reads the body: the check
  silently sees nothing.
- **One VU, one session forever.** If the app caches per session, a run with 200
  VUs exercises 200 warm sessions. Rotate credentials from the data set.
- **k6 does not execute browser JavaScript.** A 60 ms API response is not a 60 ms
  page. The `k6/browser` module drives real Chromium for frontend cost, but that
  is a small number of browsers, not a load model — keep it as a separate,
  low-VU scenario alongside the protocol-level one.
- **One generator machine has limits** — CPU, ephemeral ports, file descriptors.
  Past roughly a few thousand RPS check them explicitly; distribute with
  `k6-operator` on Kubernetes or Grafana Cloud k6 when one box is the ceiling.

## When another tool is the better answer

| Tool | Reach for it when |
| --- | --- |
| **Locust** | The project is Python and the scenarios need real application code (its own client library, an unusual auth flow). Distributes easily; closed-model by default, so mind the arrival-rate question. |
| **JMeter** | A corporate suite already exists in it, or the protocol is not HTTP (JDBC, JMS, LDAP). Powerful and ubiquitous; the XML plans age badly in code review. |
| **Gatling** | A JVM shop that wants scenarios in Scala/Java/Kotlin next to the app, with strong built-in reports. |
| **vegeta / hey / oha** | A single endpoint, constant arrival rate, from the command line in ten seconds — a sanity check or a quick before/after, not a scenario suite. |
| **`ab` (ApacheBench)** | Almost never: single-threaded, closed-model, no percentile you should trust. If it is what is installed, treat its numbers as a smoke signal only. |
| **Playwright / k6 browser** | The question is frontend cost (render, hydration, Core Web Vitals) rather than server capacity. |

The strongest reason to use any of these over k6 is that the project already
has it.
